# Autenticación por sesión: contrato de integración

El backend recibe `POST /api/auth/login` como `application/x-www-form-urlencoded`, con `correo` y `password`. Primero se obtiene `GET /api/auth/csrf`, cuya respuesta contiene `headerName` y `token`. En el mismo origen se envía esa cabecera en login y en cada POST, PUT, PATCH y DELETE. En login correcto se responde 204 y se debe obtener un token nuevo antes de otra escritura. `GET /api/auth/me` devuelve el perfil y `GET /api/auth/validate` devuelve 204 si está autenticado. No hay que exponer la cookie de sesión a JavaScript.

`POST /api/auth/logout` exige CSRF e invalida la sesión; devuelve 204. Tras logout se debe solicitar un token nuevo antes de otro login. El tiempo de inactividad configurado es 30 minutos. Se permiten varias sesiones simultáneas.

Una solicitud protegida sin sesión válida devuelve 401 `UNAUTHENTICATED`; una sesión cuya identidad cambió devuelve 401 `SESSION_INVALIDATED`. Una solicitud con sesión autenticada y token ausente o inválido devuelve 403 `CSRF_INVALID`; una cuenta autenticada sin autorización recibe 403 `ACCESS_DENIED`. Login sin token también devuelve 403 `CSRF_INVALID`. Una solicitud de escritura anónima o con sesión expirada sin token devuelve 401, salvo login. Si el token es válido, la autorización posterior decide el resultado. Las credenciales incorrectas devuelven 401 `AUTHENTICATION_FAILED`. Si no puede comprobarse la identidad de sesión, se devuelve 503 `IDENTITY_CHECK_UNAVAILABLE`.

Al recibir 401, Angular debe descartar el estado autenticado, solicitar un token para una nueva sesión anónima y presentar el login. Si recibe 403 `CSRF_INVALID`, puede obtener un token nuevo y comunicar al usuario que reintente. Nunca debe repetir automáticamente una operación de negocio rechazada. Distinguir los códigos JSON y los errores de red; una respuesta fallida de logout no demuestra que se invalidó la sesión en el servidor.

El filtro de reevaluación compara en solicitudes autenticadas que lo alcanzan la cuenta, estado, rol, permisos efectivos y una marca del hash de contraseña. Un cambio detectado invalida esa sesión al siguiente acceso; las operaciones ya en ejecución no se interrumpen. La consola de recuperación se detecta en la siguiente comprobación porque cambia el hash. El filtro se encuentra después de CSRF y logout, por lo que estos pueden finalizar antes de la reevaluación. La comparación no evita carreras entre la comprobación y una operación concurrente.

Las sesiones y la clave de la marca viven en memoria del proceso. Un reinicio invalida las sesiones; no se ofrece almacenamiento compartido ni continuidad entre instancias. La reevaluación añade una consulta a la base por solicitud autenticada y falla cerrada si esa consulta no está disponible. La configuración `deployment` fija `Secure=true` para la cookie; debe activarse únicamente en un despliegue HTTPS. El valor inicial de `SameSite` es `Lax` y `HttpOnly` está habilitado. La topología de proxy y el tratamiento de encabezados reenviados deben definirse y validarse sin confiar en cabeceras enviadas directamente por clientes.

Este documento describe la implementación prevista; no acredita pruebas ni habilita un despliegue. Los clientes Basic y las pruebas que dependen de él deben migrarse a sesión y CSRF.

Las pruebas web de autorización usan un fixture de prueba que construye el principal mediante el servicio de identidad real, mantiene activo el filtro de reevaluación y añade un token CSRF de prueba. Ese fixture simula la autenticación y no acredita el login ni el ciclo de sesión; las pruebas de autenticación y la integración MySQL del maestro usan el endpoint real de login. Los `@WithMockUser` conservados en suites de servicio controladas establecen contexto de seguridad para llamadas directas, no autentican solicitudes HTTP. La consulta pública utiliza un usuario anónimo.
